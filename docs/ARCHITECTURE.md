# LifeLine architecture

The original architecture is retained: React/Vite + shadcn/Tailwind → FastAPI → validated model inputs → baseline/heuristic/MILP → independent physical checks → typed results and deterministic explanations.

## Data paths

1. Synthetic mode: fixed daylight curve × preset/user cloud factors → 24 PV-energy values.
2. Historical mode: bundled NASA POWER hourly irradiation → shared PV conversion → 24 PV-energy values.
3. Live mode: fixed-host Open-Meteo adapter → validated, timestamped forecast/cache → IANA-local interval integration → shared PV conversion → 24 PV-energy values. Non-24-hour local days are rejected for simulation.

All three methods within a comparison receive the exact same immutable `ModelInput`. In live sensitivity runs, each explicitly labeled sunlight multiplier produces a new comparison with the same equipment, physical limits and midnight charge. No weather is generated by a language model.

## Energy model

The pure numerical layer uses `BatteryConfig`, `FlexibleTask` and immutable `ModelInput` values from `backend/app/energy_types.py`. `simulate_baseline`, `sunshine_first` and `optimize` return complete plans; `compare_schedules` runs all three with identical inputs. Canonical presets live in [scenarios.json](../contracts/scenarios.json), rather than duplicated route/UI constants.

The horizon has 24 one-hour slots and 25 stored-energy boundaries. Powers and bus limits are kW; per-slot flows and battery states are kWh. For each slot, with PV `p`, requested essential energy `c`, unserved essential energy `u`, flexible service `f`, charge input `q`, discharge output `d`, curtailed PV `w` and stored energy `e`:

```text
p[t] + d[t] = (c[t] - u[t]) + f[t] + q[t] + w[t]
e[t+1] = e[t] + eta_charge*q[t] - d[t]/eta_discharge

e[0] = initial_battery_kwh
0 <= e[b] <= battery_capacity_kwh             for boundaries 0..24
0 <= u[t] <= c[t]
0 <= w[t] <= p[t]
0 <= q[t] <= max_charge_kw * dt * z[t]
0 <= d[t] <= max_discharge_kw * dt * (1-z[t])
z[t] in {0,1}
```

Each flexible task has zero allocation outside its allowed hours, a per-slot power cap and a total allocation no greater than its required energy. Requested minus served energy is daily deferral, not an invented next-day or hourly schedule. Flexible work is divisible/interruptible; critical hours stay fixed. The baseline serves essential demand first, then requested fixed flexible work, storage and curtailment; it can use energy below the desired reserve but cannot violate physical zero.

The MILP uses ordered stages: minimize essential shortfall with optional work disabled; maximize the achievable floor capped by reserve across all boundaries; maximize flexible completion when essential demand is feasible; maximize final stored energy; then minimize battery throughput and apply stable task/hour preferences. A shortage result keeps flexible work disabled. Earlier objectives remain fixed while solving later stages. The shared five-second solve budget excludes dependency import, HTTP queue wait and serialization.

Independent raw hourly/state/daily checks precede display rounding, using `1e-6 kWh` energy tolerance:

```text
initial storage + total PV
  = final storage + essential served + flexible served + curtailment + conversion loss

conversion loss = (1-eta_charge)*sum(q) + (1/eta_discharge-1)*sum(d)
```

Status is `CRITICAL_SHORTAGE` when essential unmet energy exceeds tolerance, otherwise `RESERVE_AT_RISK` when any boundary is below reserve, otherwise `OK` (“Within modeled limits”). Zero requested essential demand has null/N/A coverage. Full-day minimum includes all 25 states; evening minimum uses boundaries 18–24; midnight energy is boundary 24. Comparisons report these separately and disclose whether completed flexible work is equal and whether sunshine-first ties the MILP. Neither `OK` nor a solver optimum establishes clinical safety.

Forecast service clocks/transports are injected for offline unit/integration tests. The local cache is bounded and does not constitute durable storage or a distributed deployment cache.

## Assistant boundary

The selected provider is **local Ollama with Llama 3.1 8B**. `GET /api/agent/status` verifies an installed model with tool capability and rejects cloud/remote model records. `POST /api/agent/ask` receives the operator's reviewed clinic, location, explicit midnight charge, question and bounded user-question history. It reads the current configuration, asks the local model for a native tool call, validates its name/arguments, and executes existing Python planning functions. Model requests use a fixed loopback URL, no provider key, a bounded context/output, at most three selections and an overall request timeout. Generated prose is never rendered as an energy answer; assessments/actions/numbers are generated from actual tool results. This is genuine LLM tool selection with a deterministic result renderer, not free-form model reasoning presented as numerical evidence.

The operator context remains authoritative. New fixed-equipment proposals require explicit user evidence for power, consecutive whole-hour runtime, earliest start and deadline. Existing protected equipment cannot be edited through agent tools. A hypothetical appliance is checked at every allowed start as fixed hourly demand; this does not validate clinical cycles. Capacity search holds initial stored kWh, forecast, reserve, efficiencies, equipment and output limits fixed. It brackets a modeled transition to within 0.25 kWh, up to 200 kWh; no charged new battery, price or certified sizing is inferred.

Native local templates sometimes encode numeric/list arguments as JSON strings. A narrow provider adapter decodes only known numeric/list fields before strict validation. HTTP user inputs remain strict. Unknown tools, unsupported arguments and malformed responses cannot execute code or write configuration. Missing inputs produce focused backend-authored questions.

The original `/api/assistant` offline rule-based editor and `/api/planner/ask` guided forecast workflow remain unchanged. Local-model connection failures, invalid calls and busy/timeout cases disclose deterministic fallback. Weather errors propagate as unavailable rather than inventing a forecast. Historical/synthetic planning remains an explicit offline alternative.

Wajo authenticated discovery and a harmless greeting were tested separately. The application neither loads its credential nor invokes Fo. No Claude integration or hosted-LLM validation is claimed. See [architecture decision and proof](DEVELOPMENT.md#provider-investigation-and-decision).

## HTTP contract and errors

Exact shapes live in [api.ts](../contracts/api.ts), [forecast.ts](../contracts/forecast.ts), [agent.ts](../contracts/agent.ts) and the generated [OpenAPI snapshot](../contracts/openapi.json). The [scheduling response example](../contracts/examples/scheduling.response.json) is documentation-only. Regenerate the schema/example with `python scripts/export_api_contract.py` after contract changes.

| Endpoint | Purpose |
|---|---|
| `GET /api/health` | Local health after startup configuration validation and SciPy import |
| `GET /api/scenarios` | Four presets with resolved defaults and synthetic provenance |
| `POST /api/simulate` | Fresh baseline/heuristic/MILP, effective inputs, computed comparison, diagnosis and per-plan warnings |
| `GET /api/demos/competing-windows` | Input-only constructed scheduling example; results are calculated through the normal simulation endpoint |
| `GET /api/agent/status`, `GET /api/agent/tools` | Actual provider readiness and allowed tool schemas |
| `POST /api/agent/ask` | Reviewed-context agent selection, validated execution and deterministic outcomes |
| `GET /openapi.json`, `GET /docs` | Machine-readable schema and optional Swagger UI; Swagger assets require internet |

The [weather reference](LIVE_WEATHER.md#http-and-structured-tools) covers forecast and guided-tool endpoints. The numerical core and bundled historical/synthetic calculations need no external services after installation; fresh forecasts require reachable weather or an explicitly valid cache.

Input resolution is common defaults → preset → explicit request overrides. Omission is distinct from zero. Reject unknown fields, explicit null where not allowed, numeric strings, booleans as numbers and nonfinite values. A smaller capacity must contain inherited or explicit initial energy and reserve; never silently clamp them.

| Physical input | Inclusive limits |
|---|---|
| Battery capacity | `0 < value <= 200` kWh |
| Initial stored energy and reserve | `0 <= value <= resolved capacity` |
| PV capacity and external charge/discharge limits | `0 <= value <= 100` kW |
| Charge/discharge efficiencies | `0 < value <= 1` |
| Additional protected load | `0 <= value <= 10` kW, only for `high_demand` |

Startup validates preset IDs, finite defaults, 24-slot profiles, equipment IDs, hours/windows, task requirements and baseline allocations. Configuration is resolved relative to the module/repository path and held as a validated startup snapshot. Valid work that cannot fit its permitted window is deferrable; malformed windows/configuration stop startup or return validation errors.

Successful calculations return HTTP 200 even for reserve risk or essential shortages. `INVALID_REQUEST` is structured 422 (404/405 retain appropriate HTTP status for invalid routes/methods). Solver unavailability, timeout and unverifiable arithmetic return structured 503; unexpected failures return 500 without stack traces. A technical error has no fabricated plan or risk result.

The backend serves `frontend/dist` and `/api` from one origin after a build. Vite development/preview proxy `/api` to the configured backend. Browser-only static hosting cannot run Python. The process-local solve lock serializes numerical work in a worker thread while health/catalog requests remain available; no production load or distributed-concurrency guarantee is implied. The current app has no durable accounts, database, device control or clinic telemetry.
